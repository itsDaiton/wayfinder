# AGENTS.md

Reference for AI agents (and contributors) working in this repository: what the project is, where decisions live, and how work is tracked and shipped.

This is the basic version. Code conventions and testing rules are added with the first real code (WAY-3, [#3](https://github.com/itsDaiton/wayfinder/issues/3)).

---

## Project

Wayfinder is a personal Android app for planning running, walking and cycling routes on a Mapy.com map. It's built with React Native (Expo) and TypeScript, and installed directly as an APK.

So far the app is an empty Expo shell; the features come from the v1 tickets.

## Source of truth

- **[docs/SPEC.md](./docs/SPEC.md)** covers the product:
  - how the app behaves (§1–8)
  - the technical decisions (§9)
  - the acceptance checklist for version 1 (§10)
- **[CONTEXT.md](./CONTEXT.md)** is the domain glossary: Route, Point, Leg, Draft, Saved route and so on. Use its terms in issues, code, tests and commits, and avoid the synonyms it lists.
- **GitHub Issues** hold the work. Version 1 is epic [#2](https://github.com/itsDaiton/wayfinder/issues/2), with one sub-issue per ticket. Version 2 is backlog epic [#17](https://github.com/itsDaiton/wayfinder/issues/17).

Keep these docs current in the same PR as the change. Docs that describe the old way are a bug, not a nit.

- How the app behaves → `docs/SPEC.md`.
- A domain term added, renamed or retired → `CONTEXT.md`.
- How the repo works (workflow, conventions) → this file.

## The app

One Expo app at the repo root. There is no backend: the app calls Mapy.com directly and keeps routes in SQLite on the phone (SPEC §9).

| Path                    | What lives there                                                                                                                 |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `src/app/`              | Screens only. Expo Router turns every file into a route, and `_layout.tsx` files define navigators.                              |
| `src/`                  | Everything else: route logic, the Route provider, storage, components. Import it with the `@/` alias (`@/foo` is `src/foo`).     |
| `assets/`               | App icon and images                                                                                                              |
| `app.json`              | Expo config: app name, Android package, plugins                                                                                  |
| `release-please-*.json` | Release Please config and the last released version (see [Versioning](#versioning))                                              |
| `pnpm-workspace.yaml`   | pnpm settings: flat `node_modules`, [supply-chain rules](#dependencies), install script approvals, peer dependency fixes         |
| `.github/`              | [CI](#ci) and Release Please workflows, [Dependabot config](#dependencies), issue and PR templates                               |
| `android/`              | Generated by `expo prebuild` and git-ignored. Never commit or hand-edit it: native settings go in `app.json` and config plugins. |
| `.vscode/`              | Shared editor settings: format on save with Prettier, ESLint fixes on save, recommended extensions                               |

### Commands

Use the Node version in `.nvmrc` and **pnpm**, the version pinned in `package.json`'s `packageManager`. `npm install` is blocked.

```bash
pnpm install          # install dependencies
pnpm android          # build the development build, install it on the phone or emulator, start Metro
pnpm start            # start Metro only, for a development build that's already installed
pnpm lint             # ESLint with Expo's config; warnings fail too
pnpm lint:fix         # ESLint with autofix
pnpm format           # Prettier, rewriting files
pnpm format:check     # Prettier, check only
pnpm typecheck        # tsc --noEmit
```

Run `lint`, `format:check` and `typecheck` before calling a change done. Tests (Jest) are added with WAY-3.

### CI

The `ci` workflow ([`.github/workflows/ci.yml`](./.github/workflows/ci.yml)) runs on every PR to `main`, Dependabot's included, except the release PR.

- **`install` runs first:** `pnpm install --frozen-lockfile`, so the [supply-chain rules](#pnpm-rules) apply. If it fails, nothing else runs.
- **Then the `lint`, `format` (`pnpm format:check`) and `typecheck` jobs run in parallel**, each reporting on its own. Jobs don't share files, so each one installs again from the pnpm store that `install` cached.
- **A new check script goes into the workflow's matrix in the same PR** (a job `name` and the `script` it runs), e.g. `test` with WAY-3.
- **Its actions are pinned to a commit hash with the version in a comment** (`uses: owner/action@<sha> # v1.2.3`). Dependabot updates both.
- **The release PR is skipped with `paths-ignore`** on the four files it changes: `.release-please-manifest.json`, `CHANGELOG.md`, `app.json` and `package.json`. Opening it does start a run, but the `release-please` workflow merges it seconds later, before the run starts its jobs, so the run fails with "a workflow file issue". The filter skips any PR that changes only those files, so run the checks locally when a PR touches only `package.json` or `app.json`.
- **It's not a required check**, because the release PR gets no run (see [Versioning](#versioning)).

Machine setup and seeing the phone screen from VS Code are in the [README](./README.md#run-it-locally).

### Expo rules

- **Add packages with `pnpm expo install <package>`**, not `pnpm add`: it picks the version that matches the Expo SDK. Where api.expo.dev is unreachable (a sandbox, say), `EXPO_OFFLINE=1 pnpm expo install <package>` takes the same versions from the installed `expo` package. Versions under 10 days old are never installed (see [Dependencies](#dependencies)).
- **A new dependency with an install script fails `pnpm install`** (`ERR_PNPM_IGNORED_BUILDS`). Check what the script does, then list the package under `allowBuilds` in `pnpm-workspace.yaml`: `true` runs it, `false` skips it.
- **Check Expo APIs against the docs for the SDK in `package.json`** (`https://docs.expo.dev/versions/v57.0.0/`), not memory. They change with every SDK.
- **The app is a development build (`expo-dev-client`), not Expo Go.** After adding a package with native code or changing `app.json` plugins, rebuild with `pnpm android`; restarting Metro isn't enough.
- `pnpm dlx expo-doctor` checks dependency versions and config.

## Dependencies

New releases wait 10 days before they reach the app, in pnpm and in Dependabot alike. Most malicious releases are found and pulled from the registry within hours or days, so the wait keeps them out.

### pnpm rules

The supply-chain settings live in `pnpm-workspace.yaml`.

- **Only versions at least 10 days old are installed** (`minimumReleaseAge`). This covers transitive dependencies and the versions already in `pnpm-lock.yaml`, so a version that's too new fails the install with `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION`, `--frozen-lockfile` included. When adding a package, pnpm picks the newest version in range that's old enough.
- **A trust downgrade fails the install** (`trustPolicy: no-downgrade`, `ERR_PNPM_TRUST_DOWNGRADE`). That's a version published with weaker evidence (trusted publisher, provenance) than earlier releases of the same package, which is what a hijacked maintainer account looks like.
- **An exception names one exact version** (`name@version`, never a bare name) in `minimumReleaseAgeExclude` or `trustPolicyExclude`, with a comment saying why. Wait out a young version rather than excluding it, unless it's an urgent security fix. Before excluding a trust downgrade, check on npm who published that version and why. pnpm drops exceptions the lockfile no longer uses.
- `autoDedupe` keeps one version of a package wherever one fits every range.
- Already on by pnpm's defaults, so not repeated in the file: dependency install scripts need approval (`allowBuilds`, see [Expo rules](#expo-rules)), and only direct dependencies may come from git or a tarball URL (`blockExoticSubdeps`).

### Dependabot

[`.github/dependabot.yml`](./.github/dependabot.yml) checks the npm packages and the GitHub Actions every week.

- **Cooldown:** 10 days, the same as pnpm. Security updates skip it, and Dependabot lifts pnpm's release age for them.
- **Titles:** `fix(deps): bump …`, so every merged Dependabot PR becomes a patch release (see [Versioning](#versioning)). Its branches are named `dependabot/…`, not by the branch rules below.
- **Expo SDK packages** (`expo`, `expo-*`, `react-native-*`, `eslint-config-expo`, `@types/react`, `typescript`) only get patch updates that stay inside the SDK's ranges, together in one `expo-sdk` PR. The SDK pins `react`, `react-dom`, `react-native`, `react-native-reanimated` and `react-native-worklets` to exact versions, so Dependabot never updates them. Security updates follow the same limits.
  - When `pnpm expo install` adds a package the SDK manages and the patterns miss it, add it to the `ignore` rules.
  - Upgrading the SDK is a separate change made by hand: follow Expo's upgrade guide for the new SDK. `pnpm expo install --check` lists the packages that don't match it.
- **Everything else:** minor and patch updates come together in one `minor-and-patch` PR, and each major update gets its own. GitHub Actions updates come in one PR.
- **The [`ci` workflow](#ci) checks these PRs** like any other: the install with the supply-chain rules, then `lint`, `format:check` and `typecheck`. It can't run the app, so after an update to a package with native code, check out the branch, rebuild with `pnpm android` and try the app.

## Git workflow

- **Never commit directly to `main`.** All work goes through a branch and a pull request.
- **Branch names:**
  - `type/way-<n>-<slug>` for ticket work, e.g. `feat/way-5-tap-to-route`
  - `type/<slug>` for work without a ticket
- **One logical change per branch.** Prefer one ticket per PR, and don't bundle unrelated changes.
- **Never commit secrets:** the Mapy.com API key, the signing keystore and its passwords stay in git-ignored files (SPEC §9.6).

### Conventional Commits everywhere

**Commit messages, PR titles and issue titles, including epics, all use [Conventional Commits](https://www.conventionalcommits.org/): `type(scope): summary`.**

- **Types: `feat` and `fix` only**, with `feat!` / `fix!` for a breaking change. This is the same rule as nebula-chat, so Release Please can be added later without rewriting history.
  - `feat`: new capability someone could use or notice, e.g. a new screen, action or documented convention.
  - `fix`: everything else, e.g. bug fixes, docs, tooling, CI, refactors, tests, dependency bumps. When in doubt, `fix`.
  - Don't use `chore`, `docs`, `refactor`, `style`, `test`, `build`, `ci` or `perf`.
- **Scope names the area** the change touches: `app`, `build`, `deps`, `planning`, `stats`, `routes`, `export`, `settings`, `backup`, `map`. `deps` is for dependency updates, Dependabot's included. Leave it out for repo-wide changes (docs, `AGENTS.md`) and for epics.
- **Summary:** lowercase, imperative, no trailing period. Keep the whole subject line under 72 characters.

### Ticket IDs

Every issue is a ticket with the key **`WAY-<issue-number>`**: issue `#5` is `WAY-5`. The key is an alias for the issue number; there is no separate counter.

- **Issue titles carry the key:** `type(scope): WAY-<n> summary`, meaning the key, a space, then the summary, with no colon after the key.
  - Ticket: `feat(planning): WAY-5 plan a route by tapping`
  - Epic: `feat: WAY-2 v1 manual route planning`
  - The issue number is only known after creating the issue, so edit the title right after.
- **The PR title is the issue title**, reused exactly.
- **The PR body has a `Closes #<n>` line.** GitHub closes issues by the bare `#n`, not by the `WAY-` key.
- **Work without a ticket** uses a plain `type(scope): summary` title.
- **Gotcha:** GitHub closes an issue when a merged PR's title, body or commits contain a closing keyword (`close`, `fixes`, `resolves`) before `#n`, even inside "do not close #n". To mention an issue a PR doesn't resolve, write "issue 5" or avoid the keyword.

### Pull requests

- Open PRs against `main`, as drafts until they're ready for review.
- Fill the template in [`.github/pull_request_template.md`](./.github/pull_request_template.md). It has:
  - a short summary of what changed and why
  - `Closes #<n>`
  - a test plan, including which SPEC §10 checklist items were checked on the phone
  - a docs checklist (SPEC, AGENTS, CONTEXT)
- Keep PRs small. A ticket too big for one PR should be split into new tickets, not left half-closed.
- **No timed check-ins on PRs.** Never schedule Routines or `send_later` reminders to re-check a PR, hourly or otherwise. The PR's own activity events (comments, reviews, CI) are enough.

## Versioning

The app has one version, kept identical in `package.json` and `app.json` (`expo.version`). **[Release Please](https://github.com/googleapis/release-please) owns it: never edit either version, `CHANGELOG.md` or `.release-please-manifest.json` by hand.**

- On every push to `main`, the `release-please` workflow opens or updates one release PR. It bumps both versions and writes `CHANGELOG.md` from the Conventional Commits since the last release.
- `feat` bumps the minor version and `fix` the patch. A `!` (breaking change) also bumps the minor version while the app is below 1.0.0. Version 1.0.0 is a deliberate step: add a `Release-As: 1.0.0` footer to a commit.
- The workflow merges the release PR itself (squash) right away, then creates the `wayfinder-v<version>` tag and a GitHub Release in the same run. So every `feat` or `fix` that lands on `main` becomes a released version. The Release holds only notes and never an APK (SPEC §9.6).
- The release PR and its commit are titled `chore(main): release wayfinder <version>`, Release Please's own format. It's the one `chore` the repo allows: it is left out of the changelog and never triggers a release itself.
- The merge and tag happen in one run because pushes made with the default token don't trigger other workflows. A workflow that should run on the tag, such as the APK build, needs a personal access token or GitHub App token in place of the default one. The release PR gets no [`ci`](#ci) run either: it's merged seconds after it opens, and `ci` skips it. So don't make a check required on `main` without changing this.
- This works because PRs are squash-merged, so the PR title becomes the commit subject on `main`.
- Actions needs "Allow GitHub Actions to create and approve pull requests" turned on in the repo settings.

## Issues

Tickets follow the skeleton in [`.github/ISSUE_TEMPLATE.md`](./.github/ISSUE_TEMPLATE.md), which pre-fills new issues in the browser.

**Sections:** Change type · Summary · Background & problem · Scope · Acceptance criteria · Technical approach & notes · Testing · Depends on · Out of scope · Notes.

**How to write one:**

- **A ticket comes before implementation.** Write it in the present or imperative tense ("Add…", "The map shows…"), never as a changelog. Acceptance criteria stay unchecked.
- **Detailed enough to implement cold,** by someone with no other context: explain the why, name the files, modules and patterns, and call out the traps and the seams to test.
- **No code snippets or line numbers.** They go stale.
- **Point to the spec.** Link the SPEC sections the ticket implements instead of restating decisions differently.
- **Use the glossary.** Name things with the terms from `CONTEXT.md`.

**Labels:**

- `enhancement` for a `feat`, `bug` for a `fix`.
- One state label:
  - `ready-for-agent`: fully specified; an agent can implement it
  - `ready-for-human`: needs the phone, secrets or accounts
- `epic` for tracking issues, plus `backlog` for an epic that hasn't started.

**Structure and dependencies:**

- Tickets are sub-issues of their epic.
- Each ticket's **Depends on** section lists its blockers, one bullet per blocker starting with `#n` (`- #3 — the Expo project`), or a single `- None (can start immediately)`.
- **Every bullet is also a native GitHub "blocked by" link**, so tools can tell which tickets are ready. Keep the two in sync: when you add or remove one, do the other.

  ```bash
  # <blocker-id> is the blocker's database id, NOT its #number:
  gh api repos/itsDaiton/wayfinder/issues/<blocker> --jq .id

  gh api --method POST repos/itsDaiton/wayfinder/issues/<n>/dependencies/blocked_by -F issue_id=<blocker-id>
  gh api --method DELETE repos/itsDaiton/wayfinder/issues/<n>/dependencies/blocked_by/<blocker-id>
  gh api repos/itsDaiton/wayfinder/issues/<n>/dependencies/blocked_by   # list blockers
  ```

- **A ticket is ready to pick up when it has no open blockers**: `gh api repos/itsDaiton/wayfinder/issues/<n> --jq .issue_dependencies_summary.blocked_by` returns `0`. A blocker must be closed, not just referenced, to unblock it.

## Architecture rules already decided

These come from SPEC §9 and apply from the first line of code:

- **Route logic is plain TypeScript** with no React or React Native imports, so it can be unit-tested with Jest.
- **Only the provider module talks to Mapy.com.** It sits behind a small interface (route, elevation, tile URL), so the provider can be swapped in one place.
- **Routes store the positions the user tapped,** not snapped ones. Snapped positions and paths are derived.
- **Estimated time is always calculated, never stored.**
